# Baton-Wrap Post-Mortem and Bulletproofing Spec (2026-07-25)

Written after Mick found that "resume from LATEST handover" would have served
him a stale baton. This note records exactly what went wrong, the evidence, and
a concrete redesign so it cannot happen again on any of the three surfaces Mick
works in.

## 1. Summary (what actually happened)

- The last good baton in the handover system is dated 2026-07-23 17:07
  ("ShareScope Pre-Webinar Hardening"). It sits in _handovers/LATEST.md and in
  _handovers/archive/.
- Today (2026-07-25) a session did real work (Portico PP1/PP2 snapshot
  automation) and wrapped it into a PROJECT pickup file:
  04-Projects/2026.04.04-ShareScope-Automation/PICKUP_POINT_2026.07.25_Portico.md
  (wrapped ~14:00).
- That work did NOT go through the baton-wrap procedure. LATEST.md was never
  overwritten and no archive copy was dropped for 25 July.
- Net effect: the next thread opening with "Cedric, resume from LATEST handover"
  would silently have loaded the 23 July baton, as if two days of Portico work
  never happened. Nothing was lost (the Portico pickup is safe), but the baton
  relay was broken and the break was invisible.

  touched since. (get_file_info, this session.)
- _handovers/archive/ newest file: "2026.07.23 - 1707 - baton - ShareScope

## 3. Root cause

Primary cause: the baton-wrap procedure assumes it is (a) triggered as a
registered skill and (b) running on a surface with direct vault + git access
(Claude Code). Today's session ran in Cowork cloud, where neither assumption held
cleanly: the skill is not in Cowork's registry, so the codified procedure never
fired, and the session fell back to an ad-hoc project pickup instead of honouring
the LATEST.md contract. The vault was actually reachable via the Filesystem
bridge, so the write COULD have happened - the procedure just was not executed.

This is the same registry-drift problem already logged on 2026-07-08 as
feedback_check_vault_skills_registry (Cowork's available_skills and the vault
skills folder disagree in both directions). It has now bitten a second time, on
a more important target.

Contributing factors (each is independently a bug worth fixing):

1. SILENT FAILURE. Nothing verifies, after a wrap, that LATEST.md now carries
   today's date. And nothing at session-start warns that LATEST.md looks stale.
   A stale baton is byte-indistinguishable from a fresh one until you read the
   date, so the relay can break with zero signal.
2. SINGLE FIXED FILE, OVERWRITE SEMANTICS. LATEST.md is one predictable path
   that gets overwritten. If the write goes to the wrong surface or silently
   no-ops, the previous baton is what gets served next time.
3. NO DEGRADED-MODE PATH. Three surfaces with three capability profiles
   (Claude Code = vault+git; Cowork = vault via bridge, ephemeral sandbox,
   registry drift; claude.ai web = no vault at all), but only one procedure,
   written for the strongest surface. The two weaker surfaces have no defined
   safe route.
4. EPHEMERAL SANDBOX. Anything a cloud session produces that is not explicitly
   written to the vault dies with the session (today's changelog did exactly
   this). A baton held only in sandbox memory is already lost.

## 4. Design goals

- The baton must NEVER exist only in ephemeral memory.
- A broken relay must be LOUD, not silent - caught at wrap time and again at
  session-start.
- One canonical read target (LATEST.md), reachable and correct from every
  vault-aware surface.
- A defined, safe route on every surface Mick uses, including claude.ai web
  which has no vault access.
- No dependence on Cowork's skill registry surfacing baton-wrap.

## 5. The hardened design

### 5.1 One contract, three delivery routes

Canonical read target stays: _handovers/LATEST.md. Every session-start reads it.
Delivery is routed by surface:

- Claude Code: write archive copy, then LATEST.md, then git commit/push. (As now.)
- Cowork (cloud or desktop): write the SAME vault files via the Filesystem /
  device bridge. Do this BEFORE the session ends (sandbox is ephemeral). Also
  deliver the baton to Mick as a file (SendUserFile) so an out-of-vault copy
  exists regardless of sandbox lifetime.
- claude.ai web (no vault): cannot write the vault. Degraded mode - output the
  full baton in-chat AND email it to Mick as a self-note with a fixed subject
  tag (e.g. "[BATON-ORPHAN] YYYY.MM.DD - topic"). The next vault-aware session
  promotes it into LATEST.md (see 5.5).

### 5.2 Freshness guard (the single most important fix)

- At WRAP end: after writing LATEST.md, RE-READ it and assert the frontmatter
  date/time equals the London "now" just computed. If it does not match, the
  write did not land - raise it loudly, do NOT report success. This check alone
  would have caught today's miss immediately.
- At SESSION START: read LATEST.md's date. Flag "STALE HANDOVER" to Mick if it
  is (a) not today when a wrap was expected, OR (b) older than the newest file
  in _handovers/archive, OR (c) older than the newest project PICKUP_POINT_* or
  orphan baton email. Turn silent staleness into a visible banner before greeting.

### 5.3 Archive-first, verify-after ordering

Always: compute time -> write the timestamped archive copy FIRST -> overwrite
LATEST.md -> re-read and verify LATEST matches. Archive-first guarantees that
even a half-finished wrap leaves a durable dated copy (this is precisely what
protected the 23 July content). Never overwrite LATEST.md in a run that has not
already written its archive copy.

### 5.4 Kill the registry dependency

Standing rule (extend feedback_check_vault_skills_registry): on any wrap request,
if the Skill tool does not list baton-wrap, READ and EXECUTE
skills/baton-wrap/SKILL.md directly from the vault. The vault SKILL.md is the
single source of truth; the registry is only a convenience trigger, never a
precondition.

### 5.5 One reconciler ("promote latest")

A small routine any vault-aware session can run: scan the newest handover
evidence across (i) _handovers/archive, (ii) project PICKUP_POINT_* files, and
(iii) orphan baton emails in Gmail; if the newest is newer than LATEST.md,
rebuild LATEST.md from it (archive-first, verify-after). This generalises the
exact fix the Portico pickup needs right now.

### 5.6 Surface stamp in every baton

Every baton frontmatter records: surface (Claude Code | Cowork-cloud |
Cowork-desktop | web) and working_dir. Makes drift diagnosable and lets the
freshness guard reason about what the authoring session could and could not do.
