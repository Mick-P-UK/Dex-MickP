NOTES: HOW SIMON SYNCS ONE CLAUDE COWORK SETUP ACROSS EVERY DEVICE

Source: "How I Sync One Claude CoWork Setup Across Every Device!" - Systems
Made Better (Simon), https://youtu.be/qIWpa582Pso
Prepared: 2026.08.02

1. THE PROBLEM HE IS SOLVING
Cowork now lives in three places: desktop app, web browser, mobile app.
Sessions, scheduled tasks and chats sync to the cloud. Your local files do
not. So a mobile Cowork session that cannot reach your operating-system
files is just generic Claude with no context. His fix: stop letting the
local folder be the source of truth.

2. THE CORE MECHANIC - TWO LAYERS
Layer 1 - identity travels as Skills. Skills attach to your Claude ACCOUNT,
not your computer, so they are reachable from mobile, web and desktop with
no connector at all. He converts the small, stable, rarely-changing
identity files (about-me, voice profile, writing rules, could also be brand
values or ICP) from markdown files in the folder into uploaded Skills.
Method is trivial: ask Claude "turn this file into a skill and offer it to
me as a download", then Customize > Skills > Add > Upload.
Layer 2 - everything else lives in cloud storage with a connector. Memory,
context map, project briefs, outputs, knowledge base. Too big and too
volatile to be Skills. It goes in a cloud folder that is BOTH synced
locally to the desktop AND readable through a Claude connector. That gives
two routes to the same single source of truth: local path when the desktop
is on, connector when it is not.

3. THE ACTUAL TRICK - ROUTING INSTRUCTIONS
This is the bit that makes it work, and it is just text. He puts a rule at
the very top of the root CLAUDE.md, and mirrors it in the account-level
global instructions and the Cowork instructions:
- "The system lives at <cloud folder path>. Read the files directly. If
they are not directly reachable in a phone or web session, read the same
files through the <Dropbox> connector instead."
- Plus a priority-one "identity gate": before doing anything, load the
about-me files from the folder; if you cannot see them, load them from the
Skills.
Two consequences worth noting. First, mobile then self-routes - in his demo
the mobile session says "no local folder is mounted, let me locate the
folder via Dropbox", which is exactly the intended behaviour. Second, he
makes voice profile conditional (only load when writing) to avoid burning
context on every session.

4. STORAGE OPTIONS HE CONSIDERED
- GitHub: rock solid, proper version control, but push/pull every session
and overkill for non-technical teams.
- Obsidian + Obsidian Sync: clean, about 4 USD/month, good if already in
Obsidian.
- Syncthing / mirroring tools: syncs desktop-to-desktop but gives no
online/mobile route, so it does not solve the problem.
- Dropbox (his choice): built-in desktop sync, "make available offline",
granular folder permissions, 2FA, and - his main argument - the Dropbox
connector can edit individual files, effectively a virtual hard drive.
Google Drive and OneDrive are named as viable alternatives.

5. THE MIGRATION, STEP BY STEP
a) Create the folder in cloud storage, right-click, make available offline.
b) Copy the entire existing Cowork folder tree into it.
c) Add the storage connector in Claude (Customize > Connectors > Add).
d) Run a consolidation task. His brief, paraphrased: I have copied my
Claude work system from <old path> to <new path>; you can see both; check
the copy is complete and flag anything missing; find every place that still
points to the old location, inside the folder and elsewhere on the machine
including global Claude instructions, and update them to the new path; make
sure CLAUDE.md tells any future Claude how to reach this folder, read
directly by default and via the connector if not; keep it short and
top-level; analyse the task first and raise any queries before acting. He
ran it on manual approval so he could watch each step, and it surfaced old
skills and scheduled tasks still pointing at stale paths.
e) Re-point the Cowork desktop app at the new folder and star it so it is
always selected.
f) Hand-edit the top-level CLAUDE.md in the hidden .claude folder yourself
- he found Claude would not do that one.
g) Hard sync rule: whenever an about-me file is edited, flag immediately
that the matching Skill must be rebuilt. Otherwise the two copies drift.
This is the weakest joint in the whole design - it is a manual reminder,
not a mechanism.

6. SECOND MACHINE
Install Claude desktop and sign in (scheduled tasks and cloud sessions are
already there), install the storage desktop app, sync the folder, make
available offline, point Cowork at it, star it. Done in minutes. One
gotcha: if the user folder name differs between machines the absolute path
breaks, so he suggests keeping usernames identical across computers.

7. SCHEDULED TASKS - THE GOTCHAS
- Cloud tasks keep running with the laptop shut; local tasks only run while
the machine is awake and the app is open.
- Set new scheduled tasks to auto-approve or they stall waiting for you.
- A task that has a local folder selected CANNOT be moved to the cloud. You
must deselect the folder, save, reopen, and only then can you switch it to
cloud. This is the single most useful practical tip in the video.
- Artifacts produced by cloud scheduled tasks did not appear in his mobile
artifacts list, so he now instructs those tasks to post the output as a
link in the chat as a workaround.

8. PROJECTS
Binding a project to a local folder pins it to that computer and kills
mobile access. His recommendation: use projects only to group chats, put
the routing instruction in the project instructions instead, and let the
folder come from the cloud path or connector. Keeps everything portable.

9. LIMITATIONS HE ADMITS
- On mobile, via connector, Claude can READ and CREATE files but cannot do
block-level edits to an existing file - it must replace it or create a new
one. So mobile cannot incrementally update its own memory files.
- Multi-user use invites edit collisions; he suggests GitHub if you need
real version control.
- His demos were all Mac; Finder-specific steps do not map to Windows.

10. MY VERIFICATION AND WHERE I WOULD PUSH BACK
Anthropic's own documentation supports the shape of this but is slightly
more generous than he implies: remote web and mobile sessions CAN read and
write local folders you have connected, but only while the desktop app is
open on that machine; if the app is closed the session keeps running and
simply loses local file access. Scheduled tasks do now run with no device
online. So the connector layer is a fallback for the machine-is-off case
rather than the only route - his design is still right, just less dramatic
than "sync is one-way".
Dropbox has shipped a dedicated Cowork plugin as well as the plain
connector, and it explicitly supports drafting text files and saving
results back, which is why his editing claim holds better for Dropbox than
for some alternatives. Worth noting the man sells a Cowork OS template and
a five-week cohort, so the "you need a system" framing is commercially
motivated - the mechanics, though, are sound and cost nothing to replicate.

11. WHAT I WOULD DO WITH THIS FOR PAIDA
You are most of the way there already and you do not need Dropbox. Google
Drive for Desktop already backs up C:\Vaults in place, so the vault is a
synced folder with a matching Claude connector. The delta is small:
a) Promote the stable identity layer to account-level Skills: the core of
CEDRIC_MEMORY.md, the house standards (UK English, ASCII rule, Notion date
format, spreadsheet footer), and the skills registry pointer. Those then
work in claude.ai and mobile with no vault access at all.
b) Add the routing paragraph at the top of the vault CLAUDE.md and in the
account global instructions: vault path first, Google Drive connector as
fallback.
c) Audit scheduled tasks for the deselect-folder-before-moving-to-cloud
trap.
d) Test the one thing I am genuinely unsure of: whether the Google Drive
connector will do block-level edits the way he claims Dropbox does. If it
will not, memory updates from mobile become append-or-replace only, and we
should design the memory files to be append-friendly rather than fight it.
My one real reservation about his design is the manual Skill-rebuild
reminder in point 5g. Two copies of your identity that only stay in step
because you remembered to say so will drift. Better would be to keep the
Skill deliberately thin and stable - who you are, house rules - and let
everything volatile live only in the vault.
