## Notes

Thinking note, 2026.08.02 evening, worked through with Cedric on the
tablet. Feeds into tomorrow's memory session.

THE OBSERVATION

The Karpathy system is flat. Two folders - raw data and wiki - and
everything lives in one or the other. That is fine for machine retrieval
but it gives me nothing to navigate by hand.

PARA is the contrast. It maps closely to how my PC folders already work,
and its real value to me is that I can find a project without AI. Open the
folder, there it is.

So the question: can I keep the flat two-folder structure and still get
PARA?

THE PROPOSAL

Move the classification out of location and into metadata. Put the PARA
coding in the YAML frontmatter and use Obsidian Bases views as the
equivalent of the PARA folders. All notes belonging to a project then
appear in one view, regardless of which of the two Karpathy folders they
physically sit in.

WHY IT WORKS - THE TWO AXES

This is the key point. The raw/wiki split is a PROVENANCE distinction:
captured versus synthesised. PARA is a PURPOSE and LIFECYCLE distinction.
They are orthogonal, which is why the overlay does not fight the flat
structure.

  Folder axis = provenance (raw / wiki)
  Property axis = PARA (project / area / resource / archive)

I am not choosing between the two systems. I am running them on different
axes.

WHAT IT FIXES

- A folder forces one home per note. A research note genuinely serving
three projects has to be duplicated or arbitrarily assigned. As a LIST
property it can belong to all three honestly.
- Archiving becomes flipping a status property rather than moving files, so
no broken links.
- Views are cheap. New project, new view, no reorganisation.

MECHANICS

Bases layers filters as "All views" then "This view", applied in sequence -
the first selects the subset, the second prunes it. So:

- One PARA.base with an all-views filter.
- A view per bucket (Projects, Areas, Resources, Archive).
- groupBy project inside the Projects view.

Minimal schema:

  type: project | area | resource
  project: LIST of links <- must be a list, that is what buys the
many-to-many
  area: link
  status: active | archived

TWO REAL PROBLEMS

1. The discipline moves and gets harder.
A folder enforces classification at save time - you cannot avoid choosing.
A property can be left blank, and a flat vault with empty frontmatter is a
swamp with no manual fallback. The capture routes (gmail-self-notes,
yt-transcript) would need to stamp these properties automatically or the
whole thing rots.

2. It only works inside Obsidian.
This is the one that stops me. Bases is an Obsidian feature. File Explorer
still shows two flat folders, and so does any script or Claude Code run
walking the tree. So this is not "PARA without folders", it is "PARA inside
Obsidian only" - and manual navigation outside the app was my whole reason
for wanting PARA.

WHERE I LANDED - STILL OPEN

Two options, not yet decided:

  A. Commit to always working inside Obsidian, and accept that the
filesystem view is flat.
  B. Keep real PARA folders and give up the flat structure.

A middle path worth testing: keep the flat structure, and have the capture
skills write a small set of PARA properties automatically, so option A
costs nothing at capture time. Then judge after a month how often I
actually needed to browse outside Obsidian.

CONNECTION TO TOMORROW

This is the same question as the memory architecture work, one layer down:
retrieval by query versus retrieval by location. Settle the principle here
and the memory answer probably falls out of it.
