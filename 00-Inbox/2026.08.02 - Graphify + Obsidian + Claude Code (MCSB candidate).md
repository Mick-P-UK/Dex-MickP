THE CLAIM IN THE VIDEO
Graphify deconstructs a repository into a knowledge graph. The video merges
that graph output into a larger Obsidian vault, so the graph insights sit
alongside everything else and Claude Code gives better answers as a result.
The Obsidian layer is the organisational and human-readable wrapper;
Graphify is the extraction engine.

WHAT GRAPHIFY ACTUALLY IS
- Open source graph builder for AI coding assistants. Nodes are concepts
(functions, classes, design decisions, document sections, diagrams); edges
are typed relationships (calls, imports, rationale_for,
semantically_similar_to).
- Code is parsed deterministically with tree-sitter, no model call needed.
Non-code sources (READMEs, PDFs, SQL, schemas) are folded in by an LLM,
which can be a local Ollama model.
- Output is three local files: an interactive graph.html, a one-page
GRAPH_REPORT.md naming the hub nodes and clusters, and a persistent
graph.json.
- Ships as a slash command plus MCP tools. For Claude Code specifically it
installs a CLAUDE.md directive and a PreToolUse hook so the agent consults
the graph before it greps raw files.
- Sold on token reduction. The vendor quotes very large multiples (70x
plus). Treat that as marketing until measured on our own material.

WHY IT MIGHT MATTER FOR MCSB
1. It attacks the exact problem we have: a corpus too big for one context
window, where flat search or embedding chunks lose the structure. A graph
keeps who-relates-to-what.
2. GRAPH_REPORT.md is close in spirit to what we want the wiki processing
agent to produce: a compact map that an agent reads first instead of
re-reading the raw material every session.
3. Edge-level detail reportedly carries relation type, confidence score and
source location. Source location at edge level is the interesting bit given
our paragraph-level audit requirement.
4. It is local and file-based, so it fits the vault-plus-git model without
adding a hosted service.

WHERE I WOULD PUSH BACK
1. It is code-first. Our corpus is Rolls-Royce annual reports, not
repositories. The deterministic tree-sitter accuracy that makes Graphify
attractive does not apply to PDFs - those go through an LLM, which is
exactly where hallucinated relationships creep in.
2. Our audit granularity requirement is hard: paragraph, quote within a
paragraph, or a specific financial table. Graphify anchors to source
locations in code files. Whether it can anchor to a table on page 187 of a
filing is the single question that decides whether this is useful or a
distraction.
3. Store proliferation. We already plan Supabase pgvector for Phase 3b RAG
plus the markdown wiki. A graph makes three stores to keep in sync. Decide
up front whether the graph is the index over the wiki or a parallel
artefact - do not let it become a second source of truth.
4. Name collision to resolve: there is a github.com/safishamsi/graphify and
a separate graphify.net project installed via pip/uv as graphifyy. Confirm
which one the video demonstrates before installing anything.

CHEAPEST NEXT TEST
Run it over the Dex-MickP vault itself rather than over the Rolls-Royce
PDFs. Zero risk, no new corpus, and it shows the output shape and the
quality of LLM-derived edges on prose we already know well. If the graph
over our own notes is useful, then try one annual report and check whether
a fact can be traced back to a specific table.

OPEN QUESTIONS
- Does the graph rebuild incrementally, or is every new filing a full
rebuild?
- Can node and edge provenance survive into the markdown wiki page, or does
it stay locked in graph.json?
- Does this replace or complement the Obsidian Web Clipper route we were
about to test?
