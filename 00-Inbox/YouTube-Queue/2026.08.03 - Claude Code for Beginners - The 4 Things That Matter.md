PART 2 - DESKTOP APP, NOT TERMINAL (position revised)
================================================================

My earlier objection was that Claude Code is a terminal tool and members
would be lost at the command line. Mick's correction stands: the Claude
desktop app has a Claude Code tab, it looks much like the Cowork interface,
and this is the documented route - Anthropic points people wanting a
graphical interface at the desktop app as the way to use Claude Code
without a terminal. Decision: everything Mick does with Claude Code, and
everything he suggests members do, goes via the desktop tab.

Two things survive that correction, and they are the better basis for the
decision anyway.

A. THE PERMISSIONS POINT SHARPENS RATHER THAN SOFTENS

A friendly interface makes it feel like a chat window while the agent still
has real read and write access to a folder on the member's machine. Members
who would have been cautious in front of a terminal will not be cautious in
front of that tab. So the safety framing matters MORE in the desktop
version, not less. The session needs an explicit segment on choosing a
working folder and on what "allow" actually means.

B. THE COWORK QUESTION IS NOW ABOUT TASK SHAPE, NOT INTERFACE

Claude Code is organised around a project directory and code-shaped work.
Cowork is built for knowledge work. Cleaner test than developer-versus-not:
- "Analyse this annual report" or "tidy my portfolio spreadsheet" -> Cowork
- "Build me something that runs repeatedly" -> Claude Code

PART 3 - PREREQUISITES AND THE CLEAN-MACHINE TEST
================================================================

Source for everything in this section: https://code.claude.com/docs/en/setup

WHAT THE QUESTION ACTUALLY WAS

Claude Code the engine and Claude Code the interface are different things.
The desktop tab is a front end; a program does the work underneath. The
question is whether the desktop app brings that engine with it or expects
one already present, because that decides whether a member is running from
a single download or whether there is a step before the step.

WHY IT IS MURKY

Most writing online about installing Claude Code says to install Node.js
first. That is largely outdated. The native installer needs no Node.js, and
even the npm route downloads a binary that does not use Node at runtime.
The folklore and the reality disagree, so it is not safe to answer from
what is commonly written.

WHAT THE DOCS DO CONFIRM (and these matter more to members than the Node
question)

- A paid plan is required: Pro, Max, Team, Enterprise or Console. The free
Claude.ai plan does NOT include Claude Code access. This is the real gate.
A member on free hits a wall before anything else happens.
- Windows 10 1809 or later, 4 GB or more RAM, and an Anthropic-supported
country.
- The desktop app is the documented graphical route, with downloads for
macOS, Windows and Linux.
- Git for Windows is optional on native Windows. Without it, Claude Code
uses PowerShell for shell commands rather than Bash.
- Native installations auto-update in the background.

WHAT THE DOCS DO NOT SETTLE

Whether launching the desktop tab on a machine with nothing else installed
simply works. That has to be tested, not assumed.

WHY "CLEAN" IS THE LOAD-BEARING WORD

My PC has Node, Git, MCP servers, a populated .claude folder and a .env.
Anything I try will work, and it will work for reasons members do not have.
That is the standard demo trap - the presenter's machine is the one machine
where the install never fails. Test on a spare laptop, a fresh Windows user
account, or a VM. Nothing else gives a true answer.

THE SANDBOXING TENSION - NAME IT, DO NOT GLOSS IT

Sandboxing is not supported on native Windows. It needs WSL 2. So the
friendly desktop route is also the unsandboxed route, and the sandboxed
route requires exactly the terminal work I am trying to spare members.
Worth stating openly in the session rather than hoping nobody asks.
